# 문서 템플릿 사용 가이드

## 개요

이 가이드는 `TEMPLATE.md`를 활용하여 모듈별 개발 문서를 작성하는 방법을 설명합니다.

## 템플릿 구조

### 1. 헤더 (필수)
```markdown
# [번호]. [모듈명]
```
- 문서의 식별자 역할
- 예: `# 6. 주문/결제`, `# 7. 회원관리`

### 2. 개발 요청사항 (필수)
**목적**: AI와 개발자가 핵심 요구사항을 즉시 파악
**작성 내용**:
- 디자인 패턴 요구사항
- 사용할 공통코드(ENUM)
- 특별한 구현 방식
- 핵심 비즈니스 규칙

**예시**:
```markdown
### 개발 요청사항

결제 구현 시 전략 패턴을 활용해 구현

결제
- `pay_way_code`: 카드, 포인트(`PAY002`)
- `pg_type_code`: 이니시스, 나이스 (`PAY005`)

공통코드(enum)가 있다면 해당 코드를 기반으로 개발 진행.
```

### 3. 현재 구현의 제한 사항 (필수)
**목적**: 불필요한 작업 방지, 스코프 명확화
**작성 내용**:
- 현재 구현에서 제외할 기능
- 고려하지 않을 예외 상황
- 의도적으로 간소화한 부분

**예시**:
```markdown
### 현재 구현의 제한 사항

배송비와 쿠폰 관련 업무는 현재 고려하지 않을 것.
상품의 재고에 대한 동시성 문제 고려하지 않을 것.
주문시 포인트 적립 고려하지 않을 것.
```

### 4. 설정 값 (해당시)
**목적**: 외부 연동이나 환경 설정이 필요한 경우
**작성 내용**:
- application.yml 또는 properties 설정
- API 키, 엔드포인트, 타임아웃 등

### 5. 주요 프로세스 (필수)
**목적**: 전체 흐름을 한눈에 파악
**작성 방법**:
- YAML 형식의 들여쓰기로 단계별 흐름 표현
- 화면, 서버, 외부 시스템 간 상호작용 명시
- 분기 처리 및 예외 상황 포함

**예시**:
```yaml
(화면) 결제하기 버튼 클릭
	→ (서버) 주문번호조회 `/api/order/generateOrderNumber`
	→ (서버) 요청 정보 생성 `/api/payments/initiate` 
	→ 결제 처리
	→ (서버) 주문 `/api/orders/order`
```

### 6. 프론트엔드 구현 세부사항 (해당시)
**목적**: 프론트엔드 개발자를 위한 상세 가이드
**작성 내용**:
- 파일 구조
- 통신 흐름 (화살표로 시각화)
- TypeScript 인터페이스
- 에러 메시지 형식
- 상태 관리 정책

### 7. 외부 시스템 연동 (해당시)
**목적**: PG사, 외부 API 등과의 연동 스펙 정의
**작성 내용**:
- 시스템별 요청/응답 포맷
- 필수/선택 필드 구분
- 성공/실패 판단 기준
- 특이사항 (Content-Type, 인코딩 등)

### 8. API 정의서 (필수)
**목적**: 백엔드 API 스펙 명세
**작성 내용**:
- HTTP Method와 엔드포인트
- Request DTO (테이블 형식)
- Response DTO (테이블 형식)
- 프로세스 (번호 매긴 단계별 설명)

**작성 팁**:
- 중첩 객체는 `List<SubDto>` 형식으로 표기하고 별도 섹션에서 정의
- 토큰에서 추출하는 필드는 명시
- 예외 발생 조건 명시

### 9. 데이터 흐름도 (DFD) (필수)
**목적**: 시나리오별 DB 테이블 변화 추적
**작성 방법**:
1. 테스트용 기본 데이터 정의
2. 시나리오별로 단계 구분
3. 각 단계에서 영향받는 테이블의 데이터 변화 표시
4. 변경사항 컬럼으로 신규/수정/삭제 표시

**예시**:
```markdown
- 시나리오 1: 상품A 단독 주문
    - 주문
        - order_base 테이블
        | order_no | member_no |
        | --- | --- |
        | 20251030O000001 | 000000000000003 |
```

### 10. 특이사항 및 주의사항 (선택)
**목적**: 놓치기 쉬운 중요 사항 강조
**작성 내용**:
- 구현 시 반드시 주의해야 할 사항
- 일반적이지 않은 처리 방식
- 버그가 발생하기 쉬운 부분

### 11. 에러 처리 전략 (선택)
**목적**: 예외 상황별 대응 방안
**작성 내용**:
- 검증 에러
- 외부 시스템 에러
- DB 트랜잭션 에러
- 각각의 보상 트랜잭션 전략

### 12. 테스트 시나리오 (선택)
**목적**: QA를 위한 테스트 케이스 제공
**작성 내용**:
- 정상 케이스
- 경계값 케이스
- 예외 케이스

## 작성 우선순위

### 필수 (반드시 작성)
1. 헤더
2. 개발 요청사항
3. 현재 구현의 제한 사항
4. 주요 프로세스
5. API 정의서
6. 데이터 흐름도

### 선택 (해당하는 경우 작성)
7. 설정 값
8. 프론트엔드 구현 세부사항
9. 외부 시스템 연동
10. 특이사항 및 주의사항
11. 에러 처리 전략
12. 테스트 시나리오

## 작성 팁

### 1. 명확성
- 애매한 표현 지양
- "약 N개", "대략" 같은 표현 대신 정확한 값 명시
- "보통", "일반적으로" 대신 구체적인 조건 명시

### 2. 완전성
- Request에 있는 모든 필드 설명
- Response의 모든 가능한 값 명시
- 예외 상황도 빠짐없이 문서화

### 3. 일관성
- 용어 통일 (예: 주문번호 vs orderNo)
- 날짜 포맷 통일
- 테이블 형식 통일

### 4. 시각화
- 복잡한 흐름은 화살표(→, ↓)로 표현
- 테이블은 마크다운 테이블로 깔끔하게
- 단계별 들여쓰기로 계층 구조 표현

### 5. 예시 활용
- 추상적인 설명보다 구체적인 예시
- 실제 데이터 값 예시 포함
- 성공/실패 케이스 모두 예시 제공

## 실전 예제

### 나쁜 예
```markdown
### API 정의서

- 주문 API
    - POST /api/order
    - Request: 주문 정보
    - Response: 성공 여부
```

### 좋은 예
```markdown
### API 정의서

- 주문
    - POST `/api/order/order`
    - Request: OrderRequest

        | 타입 | 변수명 | 설명 |
        | --- | --- | --- |
        | Long | memberNo | 회원번호 (토큰에서 추출) |
        | String | memberName | 회원명 |
        | String | phone | 전화번호 |
        | String | email | 이메일 |
        | List<BasketResponse> | goodsList | 장바구니 상품 목록 |
        | List<PayRequest> | payList | 결제 정보 목록 |

    - Response
        응답값 없음. 주문 실패 시 예외 발생.

    - 프로세스
        ```
        1. request 정보 기반으로 Entity 생성
           order_base, order_detail, order_goods
        
        2. 검증(Entity 기반)
           - 재고 검증: 주문 수량 <= 재고 수량
           - 가격 검증: 요청 가격 == DB 가격
        
        3. 결제 승인
           payList를 순회하며 결제 처리
        
        4. Entity Insert
        
        5. 후처리
           장바구니 주문 완료 여부 갱신
        ```
```

## 활용 방법

### AI 개발 지원 시
```
@module-name.md 를 기반으로 [기능명] 구현해줘
```

### 신규 모듈 작성 시
1. `TEMPLATE.md` 복사
2. 파일명: `docs/domain/[모듈명]/[모듈명].md`
3. 필수 섹션부터 작성
4. 팀원 리뷰 후 확정

### 기존 문서 보완 시
1. 템플릿과 비교하여 누락된 섹션 확인
2. 우선순위에 따라 점진적 보완
3. DFD부터 보완 추천 (가장 이해도가 높아짐)
