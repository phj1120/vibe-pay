# VibePay MSA 전환 학습 로드맵

## 1. 문서 목적

이 문서는 VibePay를 MSA 구조로 전환하는 과정에서,
내가 직접 학습해야 할 분산 시스템 주제를 단계적으로 정리한 로드맵이다.

이 문서의 범위는 `모놀리식 기능 구현`이 아니다.
모놀리식 기능 완성과 기본 테스트 정리는 별도 문서에서 다루고,
이 로드맵은 그 이후 전환 학습에만 집중한다.

핵심 학습 축:

- 서비스 경계
- 데이터 ownership
- 분산 정합성
- 장애 전파와 격리
- 운영 복잡성

## 2. 전제

- 출발점은 `api/` 단일 모듈 모놀리식이다.
- 주문, 결제, 클레임, 상품, 회원, 장바구니, 포인트가 한 프로세스 안에 있다.
- 이 로드맵의 목적은 "몇 TPS부터 MSA가 필요하다"를 증명하는 것이 아니다.
- 목표는 모놀리식에서 보이지 않던 분산 시스템 문제를 직접 겪고 설명 가능해지는 것이다.

따라서 이 문서에서는 절대 처리량 수치보다 아래를 더 중요하게 본다.

- 병목이 어디에 생기는가
- 장애가 어디까지 전파되는가
- 어떤 정합성을 즉시 보장해야 하는가
- 어떤 부분을 eventual consistency로 받아들일 수 있는가
- 어떤 기술이 새 복잡성을 만들어내는가

## 3. 학습 원칙

1. 기능 구현보다 실패 재현이 먼저다.
2. 한 단계에 하나의 분산 문제를 집중해서 본다.
3. 각 단계는 적용 전과 적용 후를 비교한다.
4. 코드 작성 자체보다 설계 판단과 회고를 우선한다.
5. 단계 종료 기준은 기능 동작이 아니라 설명 가능성이다.
6. 절대 성능 수치보다 병목 위치와 trade-off를 본다.

## 4. 선행 조건

이 로드맵을 시작하기 전에 아래는 준비되어 있어야 한다.

- 주문/결제/취소/포인트 기본 기능이 동작하는 모놀리식
- 최소한의 테스트 데이터와 기본 테스트
- 학습용으로 요청 재현과 부하 재현이 가능한 상태

모놀리식 구현 작업은 [monolith-build-handoff.md](/Users/parkh/Dev/git/Project/vibe-pay/docs/study/monolith-build-handoff.md)에서 별도로 관리한다.

## 5. 우선순위

1. 주문 경계 분리 기준 수립
2. 서비스별 DB ownership 강제
3. 순수 동기 호출만으로 서비스 연결
4. Circuit Breaker + Cache
5. 동시성 문제 재현 후 Redis 락 또는 예약 모델
6. 순진한 이벤트 발행 후 Outbox 도입
7. 주문-결제 Saga
8. Claim Saga + 통합 장애 훈련

## 6. 공통 관찰 포인트

애플리케이션:

- latency 변화
- timeout 발생 여부
- error rate
- thread pool/connection pool 고갈 지점
- retry/circuit breaker 동작 양상

DB:

- slow query
- lock wait / deadlock
- connection 증가 양상
- 특정 테이블 또는 쿼리 집중 현상

메시징/캐시:

- Kafka lag
- consumer backlog
- Redis hit ratio
- 락 획득 실패율

도메인 정합성:

- oversell 여부
- 중복 주문/중복 결제 여부
- 포인트 이중 차감 여부
- 이벤트 유실/중복 여부

## 7. 단계별 로드맵

### 단계 1. 주문 경계 분리 기준 수립

학습 목표:

- 주문 aggregate의 진짜 경계를 정의한다.
- 주문이 현재 어떤 외부 책임과 과하게 엮여 있는지 식별한다.

직접 판단할 것:

- `order_base`, `order_detail`, `order_goods` ownership
- 주문 상태 모델
- 상품 스냅샷으로 들고 올 필드
- basket/payment/point를 주문 트랜잭션에서 분리해야 하는 이유

관찰할 것:

- 주문 생성이 현재 몇 개 도메인을 동시에 건드리는가
- 주문 부하가 올라갈 때 어떤 쿼리와 어떤 로직이 같이 느려지는가
- shared repository/shared entity 재사용 욕구가 왜 생기는가

종료 기준:

- 주문 책임 목록이 문서화되어 있다.
- future `order-service`의 소유 엔티티/유스케이스/외부 의존이 정리되어 있다.
- 무엇을 먼저 분리하고 무엇을 나중에 남길지 설명할 수 있다.

### 단계 2. 서비스별 DB ownership 강제

학습 목표:

- 프로세스 분리와 데이터 분리가 별개라는 점을 체감한다.

직접 판단할 것:

- schema-per-service 전략
- 서비스별 DB 계정 분리 기준
- FK 제거 후 대체 수단
- snapshot 허용 범위

관찰할 것:

- 조인이 사라질 때 읽기 모델이 얼마나 불편해지는가
- shared DB 상태에서 병목이 서비스가 아니라 DB 전체에 걸리는가
- 중복 저장이 읽기 단순화 대신 어떤 쓰기 복잡성을 만드는가

종료 기준:

- 서비스별 ownership 기준이 문서화되어 있다.
- FK 제거 및 snapshot 전략이 정리되어 있다.
- 즉시 일관성과 지연 허용 일관성을 구분해 설명할 수 있다.

### 단계 3. 순수 동기 HTTP 연결

학습 목표:

- 원격 호출이 메서드 호출과 전혀 다르다는 점을 체감한다.

직접 판단할 것:

- `order -> core`, `order -> goods`, `order -> payment` 내부 API 계약
- timeout 기준
- 실패 시 사용자 응답 방식

관찰할 것:

- 주문 1건이 만드는 네트워크 hop 수
- 어느 의존 서비스 지연이 전체 주문 latency를 가장 크게 올리는가
- pool 고갈과 연쇄 timeout이 어디서 시작되는가

종료 기준:

- 동기 호출 경로와 실패 전파 경로를 설명할 수 있다.
- 어떤 호출은 동기여야 하고 어떤 호출은 비동기로 바꿔야 하는지 설명할 수 있다.

### 단계 4. Circuit Breaker + Cache

학습 목표:

- 원격 의존성과 반복 조회를 완화하는 기술을 학습한다.

직접 판단할 것:

- breaker 적용 대상
- timeout/retry 위치
- cache-aside 허용 데이터

관찰할 것:

- 반복 조회가 latency와 DB read 부하에 주는 영향
- retry storm이 장애를 어떻게 키우는가
- breaker 도입 전후 장애 전파 범위 차이

종료 기준:

- 빠른 실패가 왜 더 건강한지 설명할 수 있다.
- 캐시를 저장소가 아닌 최적화 수단으로 다룰 수 있다.

### 단계 5. 동시성 문제 재현 후 Redis 락 또는 예약 모델

학습 목표:

- 분산 환경의 정합성 문제를 별도 설계 주제로 다룬다.

직접 판단할 것:

- 재고 차감 모델: 즉시 차감 vs 예약 재고
- 포인트 차감 보호 방식
- 락 키 범위, TTL, 재시도 정책

관찰할 것:

- 동시 주문 시 oversell 발생 여부
- 락 도입이 처리량과 정합성에 주는 trade-off
- DB lock, Redis lock, 예약 모델의 차이

종료 기준:

- 락이 해결하는 것과 해결하지 못하는 것을 설명할 수 있다.
- 정합성을 위한 모델링 변경 필요성을 설명할 수 있다.

### 단계 6. 순진한 이벤트 발행 후 Outbox 도입

학습 목표:

- dual write 문제를 직접 겪고 Outbox 필요성을 이해한다.

직접 판단할 것:

- 이벤트 계약
- 유실/중복 중 더 위험한 리스크
- consumer 멱등성 기준 키

관찰할 것:

- DB commit 성공 후 이벤트 발행 실패 시 어떤 문제가 생기는가
- 재시도 시 중복 이벤트가 어떤 운영 문제를 만드는가
- backlog 증가가 eventual consistency 지연을 어떻게 키우는가

종료 기준:

- Outbox가 왜 필요한지 설명할 수 있다.
- exactly-once 대신 어떤 멱등성이 필요한지 설명할 수 있다.

### 단계 7. 주문-결제 Saga

학습 목표:

- 단일 트랜잭션 대신 보상 트랜잭션으로 흐름을 설계한다.

직접 판단할 것:

- 상태 전이표
- `OrderCreated -> PaymentApproved/Failed -> OrderConfirmed/Cancelled`
- 결제 실패 시 복구 범위
- 중복 이벤트/순서 역전 대응

관찰할 것:

- PG 지연과 실패율 증가가 주문 처리에 주는 영향
- 응답 속도와 후속 상태 반영 지연의 trade-off
- 전체 중단 대신 부분 지연을 선택하는 구조의 장단점

종료 기준:

- rollback과 compensation의 차이를 설명할 수 있다.
- 자동 복구와 운영자 개입이 필요한 상태를 구분할 수 있다.

### 단계 8. Claim Saga + 통합 장애 훈련

학습 목표:

- 더 복잡한 분산 워크플로우를 상태 기반으로 운영한다.

직접 판단할 것:

- 부분 취소 금액 배분
- `PaymentCancelled`와 `PointRefunded` 합류 조건
- 한쪽 성공 후 다른 쪽 실패 시 보상 전략

관찰할 것:

- 취소 요청 몰림 시 claim/payment/core 병목 지점
- Kafka/Redis/PG 장애 시 연쇄 전파 양상
- 어떤 기능은 유지하고 어떤 기능은 지연시켜야 하는지

종료 기준:

- 완료 조건과 중간 상태를 모델링할 수 있다.
- 자동 복구와 수동 개입 경계를 설명할 수 있다.

3. 기술 또는 패턴 적용

5. 회고 또는 ADR 작성
