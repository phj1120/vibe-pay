# VibePay MSA 학습 로드맵

## 1. 목표

이 문서는 VibePay를 `완전한 MSA 구조의 커머스`로 바꾸는 과정에서,
무엇을 어떤 순서로 직접 구현해야 학습 효과가 큰지 정리한다.

대상:

- 커머스 도메인 경험은 충분하다.
- 도메인 단위 API 분리 + 단일 DB 구조에는 익숙하다.
- 하지만 서비스별 데이터 소유권, eventual consistency, 분산 트랜잭션, 대규모 트래픽 대응은 깊게 다뤄보지 않았다.

따라서 이 문서의 중심은 `기능 완성`이 아니라 아래 4가지다.

- 서비스 경계
- 데이터 소유권
- 분산 정합성
- 운영 복잡성

여기에 더해, 모든 단계는 `대용량 트래픽에서 이 구조가 왜 필요한가`를 함께 검증한다.
즉 이 커리큘럼에서 트래픽 학습은 별도 부록이 아니라 본편이다.

## 2. 학습 원칙

1. 구현보다 실패 재현이 먼저다.
2. 한 단계에 하나의 분산 문제만 다룬다.
3. 각 단계마다 `적용 전`과 `적용 후`를 비교한다.
4. 설계 판단은 직접 하고, 반복 코드는 AI에 맡긴다.
5. 단계 종료 기준은 기능 동작이 아니라 `왜 이 기술이 필요했는지 설명 가능` 여부다.
6. 각 단계는 반드시 `트래픽/병목/장애 전파` 관점의 실험을 하나 이상 포함한다.

## 3. 직접 할 일 vs AI에 맡길 일

### 직접 할 일

- 서비스 경계 정의
- 주문/결제/클레임 상태 전이 설계
- 이벤트 계약 설계
- 보상 트랜잭션 규칙 정의
- DB ownership과 FK 제거 기준 정의
- 캐시 대상/비대상 판단
- 락 범위, TTL, 재시도 정책 설계
- 병목 가설 수립과 관찰 포인트 정의
- 장애 시나리오와 회고 문서화

### AI에 맡길 일

- 모듈 스캐폴딩
- Gradle 설정
- Docker Compose 수정
- Feign/Kafka/Redis 보일러플레이트
- 반복 DTO/엔티티/리포지토리 생성
- 테스트 기본 셋업
- Flyway 마이그레이션 초안

## 4. 현재 코드 기준 우선순위

현재 저장소는 아래 상태다.

- `gateway-service`, `core-service`, `goods-service`, `payment-service`, `claim-service`는 일부 존재
- 주문 책임은 아직 `monolith`에 남아 있음
- 즉, 가장 큰 현실 갭은 `문서엔 order-service가 있는데 실제론 없다`는 점

따라서 가장 먼저 직접 설계할 축은 `order-service`다.

우선순위:

1. `order-service` 독립과 주문 aggregate 경계 설계
2. 서비스별 DB ownership 강제
3. 동기 API 호출만으로 연결해 분산 호출 고통 체감
4. Circuit Breaker + cache 도입
5. 재고/포인트 동시성 문제 재현 후 Redis 락/예약 모델 도입
6. Outbox 없는 이벤트 발행 실험 후 Outbox 도입
7. 주문-결제 Saga 완성
8. Claim Saga와 통합 장애 훈련

## 5. 공통 관찰 지표

각 단계에서 최소한 아래 지표를 함께 본다.

애플리케이션:

- RPS/TPS
- p50, p95, p99 latency
- error rate
- timeout 수
- thread pool/connection pool 사용량
- retry 횟수
- circuit breaker open 횟수

DB:

- slow query
- lock wait / deadlock
- connection 수
- CPU/IO 사용량

메시징/캐시:

- Kafka lag
- consumer 처리량
- Redis hit ratio
- Redis command latency
- 락 획득 실패율

도메인 정합성:

- oversell 여부
- 중복 주문/중복 결제 여부
- 포인트 이중 차감 여부
- 이벤트 유실/중복 여부

## 6. 단계별 상세 계획

진행 기간은 단계마다 다르다.
간단한 단계는 며칠 안에 끝날 수 있고, 복잡한 단계는 1~2주 이상 걸릴 수 있다.
중요한 것은 일정 준수가 아니라 `실패 재현`, `설계 판단`, `회고 산출물`이 모두 남았는지다.

### 단계 1. `order-service` 독립

학습 목표:

- 서비스 경계를 실제 배포 단위와 코드 단위로 체감한다.
- 주문 aggregate가 어디까지 책임지는지 직접 정의한다.

직접 설계할 것:

- `order_base`, `order_detail`, `order_goods`의 ownership
- 주문 상태값 (`PENDING`, `PAID`, `CANCELLED` 등)
- 상품 정보 중 어떤 값은 snapshot으로 들고 올지
- basket/payment/point를 왜 주문 트랜잭션에서 분리해야 하는지

먼저 겪을 문제:

- shared entity를 그대로 재사용하고 싶어진다.
- “분리했지만 결국 monolith랑 다를 게 없지 않나?”라는 의문이 든다.

트래픽 관점에서 함께 볼 것:

- 주문 API만 별도 프로세스로 분리했을 때 병목 지점이 어디로 이동하는가
- 주문 트래픽이 늘어도 다른 도메인과 독립적으로 확장할 수 있는가
- 아직 shared DB일 때 실제 병목은 애플리케이션보다 DB에 더 남아 있지 않은가

이 단계의 핵심 질문:

- 주문의 진짜 aggregate root는 무엇인가?
- 주문 생성 시 즉시 확정되어야 하는 데이터와 아닌 데이터는 무엇인가?

### 단계 2. 서비스별 DB ownership 강제

학습 목표:

- 프로세스 분리와 데이터 소유권 분리가 별개의 문제임을 배운다.

직접 설계할 것:

- schema-per-service 전략
- 서비스별 DB 계정 분리 기준
- FK 제거 후 대체 수단
- snapshot 컬럼과 중복 데이터 허용 범위

먼저 겪을 문제:

- 조인이 사라진다.
- 즉시 일관성이 약해진다.
- 읽기 모델이 불편해진다.

트래픽 관점에서 함께 볼 것:

- shared DB가 유지될 때 고트래픽 상황에서 어느 서비스가 아닌 DB 전체가 병목이 되는가
- 서비스 분리는 했는데 DB가 하나면 스케일 아웃 효과가 실제로 얼마나 제한되는가
- snapshot 중복 저장이 read 부담을 줄이는 대신 write 복잡성을 얼마나 늘리는가

이 단계의 핵심 질문:

- 어떤 데이터는 중복 저장해도 되는가?
- 어떤 일관성은 즉시 필요하고, 어떤 일관성은 지연되어도 되는가?

### 단계 3. 순수 동기 HTTP 연결

학습 목표:

- 네트워크 호출이 메서드 호출과 다르다는 점을 체감한다.

직접 설계할 것:

- `order -> core`, `order -> goods`, `order -> payment` internal API 계약
- timeout 기준
- 실패 시 사용자에게 어떤 응답을 줄지

먼저 겪을 문제:

- 한 서비스가 느리면 주문 전체가 느려진다.
- 연쇄 timeout이 생긴다.

트래픽 관점에서 함께 볼 것:

- 주문 1건이 몇 번의 네트워크 hop을 만드는가
- 상품/회원/결제 중 어느 서비스 지연이 전체 주문 latency를 가장 크게 올리는가
- 트래픽이 올라가면 thread pool과 connection pool이 어디서 먼저 고갈되는가

이 단계의 핵심 질문:

- 이 호출은 정말 동기여야 하는가?
- 실패하면 바로 사용자에게 실패를 반환해야 하는가?

### 단계 4. Circuit Breaker + Cache

학습 목표:

- 원격 의존성과 반복 조회를 완화하는 기술을 이해한다.

직접 설계할 것:

- 어떤 API에 Circuit Breaker를 둘지
- retry와 timeout을 어느 계층에 둘지
- 어떤 데이터는 cache-aside로 캐시해도 되는지

먼저 겪을 문제:

- 상품/회원 조회 지연
- retry storm
- stale cache

트래픽 관점에서 함께 볼 것:

- 인기 상품 조회, 회원 검증 반복 호출이 p95 latency를 얼마나 악화시키는가
- cache-aside 도입 전/후 DB read 부하가 얼마나 달라지는가
- Circuit Breaker가 없을 때와 있을 때 장애 전파 범위가 어떻게 달라지는가

이 단계의 핵심 질문:

- 빠르게 실패시키는 것이 왜 더 건강한가?
- 캐시는 저장소인가, 최적화 수단인가?

### 단계 5. 동시성 문제 재현 후 Redis 락

학습 목표:

- 분산 환경에서 동시성은 별도의 설계 주제라는 점을 배운다.

직접 설계할 것:

- 재고 차감 모델: 즉시 차감 vs 예약 재고
- 포인트 차감 보호 방식
- Redis 락 키 범위, TTL, 재시도 정책

먼저 겪을 문제:

- oversell
- 중복 포인트 차감
- 검증 후 차감 실패

트래픽 관점에서 함께 볼 것:

- 플래시 세일처럼 특정 상품에 요청이 몰릴 때 oversell이 실제로 발생하는가
- 락을 도입하면 처리량은 얼마나 줄고, 정합성은 얼마나 개선되는가
- 락 없는 모델, DB lock, Redis lock, 예약 재고 모델의 trade-off는 무엇인가

이 단계의 핵심 질문:

- 락은 정합성을 보장하는가, 경쟁 확률을 낮추는가?
- DB lock만으로 충분하지 않은 이유는 무엇인가?

### 단계 6. 순진한 이벤트 발행 후 Outbox 도입

학습 목표:

- dual write 문제가 왜 위험한지 체감한다.

직접 설계할 것:

- 이벤트 계약
- 유실/중복 중 어떤 리스크가 더 큰지
- consumer 멱등성 기준 키

먼저 겪을 문제:

- DB commit 성공 후 Kafka 발행 실패
- 재시도로 인한 중복 이벤트

트래픽 관점에서 함께 볼 것:

- 주문량이 증가할수록 이벤트 유실/중복이 운영에 주는 영향이 어떻게 커지는가
- consumer backlog가 쌓일 때 eventual consistency 지연이 어디까지 허용 가능한가
- throughput을 올리기 위해 consumer를 늘리면 멱등성 요구가 어떻게 더 강해지는가

이 단계의 핵심 질문:

- exactly once를 목표로 해야 하는가?
- 실제로는 어떤 형태의 멱등성이 필요한가?

### 단계 7. 주문-결제 Saga

학습 목표:

- 단일 `@Transactional` 대신 보상 트랜잭션으로 일관성을 맞추는 법을 배운다.

직접 설계할 것:

- 상태 전이표
- `OrderCreated -> PaymentApproved/Failed -> OrderConfirmed/Cancelled`
- 결제 실패 시 복구 범위
- 중복 이벤트/순서 뒤바뀜 대응

먼저 겪을 문제:

- 결제 성공 후 주문 상태 갱신 실패
- 결제 실패 후 일부 상태만 반영

트래픽 관점에서 함께 볼 것:

- PG 지연이나 실패율 증가가 주문 전체 처리량과 실패율에 어떤 영향을 주는가
- Saga 기반 전환 후 사용자 응답은 빨라졌는지, 대신 후속 상태 반영 지연은 얼마나 생기는가
- 장애 시 전체 중단보다 부분 지연을 선택하는 구조가 왜 고트래픽에 유리한가

이 단계의 핵심 질문:

- rollback이 아니라 보상이라는 말의 의미는 무엇인가?
- 운영자 수동 개입이 필요한 중간 상태는 무엇인가?

### 단계 8. Claim Saga + 통합 장애 훈련

학습 목표:

- 더 복잡한 분산 워크플로우를 상태 기반으로 설계한다.

직접 설계할 것:

- 부분 취소 금액 배분
- `PaymentCancelled`와 `PointRefunded` 합류 조건
- 한쪽 성공 후 다른 쪽 실패 시 보상 전략

먼저 겪을 문제:

- PG 취소만 성공
- 포인트 환불만 성공
- 재처리와 중복 처리

트래픽 관점에서 함께 볼 것:

- 취소 요청이 몰릴 때 claim/payment/core 간 병목은 어디서 먼저 생기는가
- Kafka/Redis/PG 중 하나가 느려지거나 멈췄을 때 연쇄 장애가 어떻게 전파되는가
- 최종적으로 어떤 기능은 유지하고 어떤 기능은 지연시키는 게 현실적인지 판단할 수 있는가

이 단계의 핵심 질문:

- 완료 조건을 어떻게 모델링할 것인가?
- 자동 복구와 수동 개입의 경계는 어디인가?

## 7. 단계 운영 방식

각 단계는 아래 순서로 진행한다.

1. 문제 정의
2. 실패 시나리오 재현
3. 패턴/기술 적용
4. 적용 전/후 비교
5. 회고 또는 ADR 작성

권장 리듬:

- 가벼운 단계: `며칠`
- 보통 단계: `약 1주`
- 무거운 단계: `1~2주 이상`

단계를 서두르지 말고, 아래 질문에 답할 수 있을 때 다음 단계로 넘어간다.

- 왜 기존 방식이 문제였는가?
- 왜 이번 기술이 필요한가?
- 적용 후 어떤 복잡성이 새로 생겼는가?

## 8. 단계별 체크리스트

### 단계 1 체크리스트

- `order-service` 경계를 정의했다.
- 주문 상태 모델을 문서화했다.
- 모듈 스캐폴딩을 만들었다.
- 주문 API 분리 후 병목 이동을 관찰했다.
- 회고: “지금 주문 책임은 왜 monolith에 남아 있었나?”

### 단계 2 체크리스트

- DB ownership 분리 기준을 정했다.
- schema-per-service 초안을 만들었다.
- FK 제거와 snapshot 전략을 정했다.
- shared DB가 병목이 되는 양상을 정리했다.
- 회고: “서비스는 쪼갰는데 DB는 왜 그대로 두고 싶어졌나?”

### 단계 3 체크리스트

- 동기 HTTP 호출만으로 주문 플로우를 연결했다.
- timeout/에러 양상을 관찰했다.
- hop 수, latency, pool 고갈 지점을 관찰했다.
- 회고: “원격 호출은 어디서부터 비싸졌는가?”

### 단계 4 체크리스트

- Circuit Breaker, retry, cache-aside를 도입했다.
- 상품/회원 조회 병목을 비교했다.
- cache 전/후 read 부하와 breaker 전/후 장애 전파를 비교했다.
- 회고: “어떤 실패는 빠르게 실패하는 게 더 낫나?”

### 단계 5 체크리스트

- 동시 주문/동시 포인트 사용 시나리오를 만들었다.
- Redis 락 또는 예약 재고 모델을 적용했다.
- oversell 방지 효과와 처리량 감소를 비교했다.
- 회고: “락 없이도 풀 수 있는 모델은 없나?”

### 단계 6 체크리스트

- 순진한 이벤트 발행을 먼저 실험했다.
- Outbox로 교체했다.
- consumer 멱등성을 반영했다.
- backlog, lag, 중복 처리 양상을 관찰했다.
- 회고: “유실과 중복 중 무엇이 더 위험했나?”

### 단계 7 체크리스트

- 주문-결제 Saga를 완성했다.
- 실패/보상 시나리오를 실험했다.
- PG 지연/실패율 증가 시 처리량과 지연 변화를 관찰했다.
- 회고: “어떤 상태는 자동 복구할 수 없었나?”

### 단계 8 체크리스트

- Claim Saga를 구현했다.
- Kafka/Redis/PG 장애 훈련을 했다.
- Strangler 전환 리허설을 했다.
- 연쇄 장애와 graceful degradation 기준을 정리했다.
- 회고: “실제 운영이면 가장 먼저 터질 지점은 어디였나?”

## 10. 단계별 공통 부하 실험

각 단계에서 아래 중 최소 1개를 함께 수행한다.

- 읽기 부하: 상품 목록/상세, 주문 완료 화면 조회
- 쓰기 부하: 장바구니 담기, 주문 생성, 포인트 사용
- 연쇄 부하: 주문 생성 후 결제 승인/실패
- 이벤트 부하: `OrderCreated`, `PaymentApproved/Failed`, `OrderConfirmed`
- 경합 부하: 한정 수량 상품 동시 주문
- 장애 부하: goods 지연, payment 장애, Kafka 지연, Redis 지연

권장 관찰 포인트:

- p95 latency
- error rate
- DB 병목
- Kafka lag
- Redis hit ratio
- oversell/중복/유실 여부

## 11. 학습 종료 기준

아래 질문에 답할 수 있으면 학습이 잘 된 것이다.

- 왜 shared DB는 서비스 분리의 착시를 만드는가?
- 왜 주문과 결제를 단일 트랜잭션으로 묶을 수 없는가?
- 왜 Outbox가 필요한가?
- 왜 Saga는 rollback이 아니라 보상인가?
- 왜 일부 일관성은 eventual consistency로 받아들여야 하는가?
- 왜 락과 캐시는 기능보다 운영 관점에서 더 어렵게 느껴지는가?
- 왜 고트래픽 환경에서는 성능 문제와 정합성 문제가 분리되지 않는가?
- 왜 MSA의 장점은 단순히 “트래픽을 많이 받는다”가 아니라 “병목과 장애를 국소화한다”는 데 있는가?
